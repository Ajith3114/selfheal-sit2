============================================================
 6F School of IT  -  SCENARIO 5
 "Where does the data on this page come from?"
============================================================

WHAT YOU BUILD
--------------
One tiny web page on an EC2 server, and one MySQL database on RDS.
The page asks the database for rows and prints them.

Then you switch the database off, and watch what happens to the page.

That is the whole scenario. No private subnets, no Multi-AZ, no
subnet groups, no NAT gateway. Default VPC, four moving parts:

    YOU  ->  EC2 (the page)  ->  RDS (the data)


WHY THIS ONE MATTERS FOR SUPPORT WORK
-------------------------------------
A ticket arrives saying "the site is broken".
Very often the site is perfectly fine and the DATABASE is down.
Telling those two apart is the job. Step 8 shows you the difference
with your own eyes.


WHAT YOU NEED
-------------
- An AWS account (free tier is enough)
- A terminal with the AWS CLI logged in  (run: aws sts get-caller-identity)
- About 45 minutes

Time to finish: ~45 min. Cost if you delete it the same day: a few cents.


------------------------------------------------------------
 STEP 1 - Pick a password and keep it somewhere
------------------------------------------------------------
WHY: you will type it about five times. RDS also refuses some
characters, so choose one that will not be rejected.

RULES: 8 to 41 characters. Do NOT use  /  "  @  or spaces.

Write it down now, for example:   Workshop2026db

Everywhere below that says YOUR-PASSWORD, use this.


------------------------------------------------------------
 STEP 2 - Make a security group for the database
------------------------------------------------------------
WHY: a database with an open door gets found. An exposed MySQL
port is scanned and attacked within hours - not days. So the
door only opens for your own laptop.

    VPC=$(aws ec2 describe-vpcs --filters Name=isDefault,Values=true \
            --query 'Vpcs[0].VpcId' --output text)

    DBSG=$(aws ec2 create-security-group \
             --group-name workshop-db-sg \
             --description "Scenario 5 database" \
             --vpc-id $VPC --query 'GroupId' --output text)

    MYIP=$(curl -s https://checkip.amazonaws.com)

    aws ec2 authorize-security-group-ingress --group-id $DBSG \
      --protocol tcp --port 3306 --cidr $MYIP/32

    echo "database security group: $DBSG"
    echo "your ip: $MYIP"

NOTE: never put 0.0.0.0/0 on port 3306. That is the single
setting that causes most "my database got wiped" stories.

If your internet connection changes (new wifi, mobile hotspot),
your IP changes too and you must add the new one:

    MYIP=$(curl -s https://checkip.amazonaws.com)
    aws ec2 authorize-security-group-ingress --group-id $DBSG \
      --protocol tcp --port 3306 --cidr $MYIP/32


------------------------------------------------------------
 STEP 3 - Create the database
------------------------------------------------------------
WHY: this is the part that holds the data. Nothing about it is
special yet - it is a normal MySQL, and AWS runs it for you.

    aws rds create-db-instance \
      --db-instance-identifier workshop-db \
      --db-instance-class db.t4g.micro \
      --engine mysql \
      --master-username admin \
      --master-user-password 'YOUR-PASSWORD' \
      --allocated-storage 20 \
      --vpc-security-group-ids $DBSG \
      --publicly-accessible \
      --backup-retention-period 0 \
      --no-multi-az

It takes 5 to 10 minutes. Wait for it properly instead of guessing:

    aws rds wait db-instance-available --db-instance-identifier workshop-db

(--publicly-accessible is here only to keep this scenario simple.
A real production database does NOT get this. That is a later lesson.)


------------------------------------------------------------
 STEP 4 - Get the endpoint (the database's address)
------------------------------------------------------------
WHY: your app needs to know where the database is. This hostname
is the one thing you must copy correctly.

    aws rds describe-db-instances --db-instance-identifier workshop-db \
      --query 'DBInstances[0].Endpoint.Address' --output text

It looks like:

    workshop-db.abcdefgh1234.ap-south-1.rds.amazonaws.com

Copy it. This is YOUR-ENDPOINT everywhere below.


------------------------------------------------------------
 STEP 5 - Launch the web server (EC2)
------------------------------------------------------------
Console is easier for this one.

  1. EC2  ->  Launch instance
  2. Name: workshop-app
  3. AMI: Amazon Linux 2023
  4. Type: t3.micro (or t2.micro)
  5. Key pair: create one, download the .pem, keep it safe
  6. Network settings -> Allow HTTP traffic from the internet: TICK IT
  7. Launch

Then note two things from the instance page:
  - its PUBLIC IP        (you open this in the browser)
  - its SECURITY GROUP id (starts with sg-)

Now let the app server reach the database as well:

    APPSG=sg-PUT-THE-EC2-SECURITY-GROUP-HERE

    aws ec2 authorize-security-group-ingress --group-id $DBSG \
      --protocol tcp --port 3306 --source-group $APPSG

WHY: the database door now opens for two things only - your laptop,
and this one server. Nothing else on the internet.


------------------------------------------------------------
 STEP 6 - Create the table and put one row in it
------------------------------------------------------------
Do this from your laptop. Install a MySQL client if you do not have one.

    # Amazon Linux 2023 / Fedora:  sudo dnf install -y mariadb105
    # Ubuntu / Debian:             sudo apt install -y mysql-client
    # Mac:                         brew install mysql-client
    # Windows:                     use MySQL Workbench, or run this from the EC2 box

    mysql -h YOUR-ENDPOINT -u admin -p

Type your password when asked, then paste this:

    CREATE DATABASE workshop;
    USE workshop;
    CREATE TABLE messages (
      id   INT AUTO_INCREMENT PRIMARY KEY,
      text VARCHAR(200) NOT NULL
    );
    INSERT INTO messages (text) VALUES ('Hello from RDS');
    SELECT * FROM messages;
    EXIT;

If SELECT shows your row, the database half is finished.


------------------------------------------------------------
 STEP 7 - Put the page on the server
------------------------------------------------------------
Connect to the EC2 box:

    ssh -i your-key.pem ec2-user@EC2-PUBLIC-IP

Install a web server and PHP:

    sudo dnf install -y httpd php php-mysqlnd
    sudo systemctl enable --now httpd

Now copy index.php from this S5 folder onto the server, and edit
the three lines at the top:

    sudo nano /var/www/html/index.php

Set:
    $DB_HOST = "YOUR-ENDPOINT";
    $DB_USER = "admin";
    $DB_PASS = "YOUR-PASSWORD";

Save (Ctrl+O, Enter, Ctrl+X).

Open in your browser:

    http://EC2-PUBLIC-IP/

You should see "Messages" and the row you inserted, with a green
"database connected" line.


------------------------------------------------------------
 STEP 8 - Prove the page is not the data
------------------------------------------------------------
Go back to the mysql prompt and add another row:

    mysql -h YOUR-ENDPOINT -u admin -p
    USE workshop;
    INSERT INTO messages (text) VALUES ('I added this without touching the code');
    EXIT;

Reload the browser.

The new line is there. You did not edit index.php. You did not
restart anything. You did not deploy.

    THE PAGE IS NOT THE DATA.
    The code decides the SHAPE. The database decides the CONTENT.


------------------------------------------------------------
 STEP 9 - Now switch the database off
------------------------------------------------------------
This is the step to pay attention to.

    aws rds stop-db-instance --db-instance-identifier workshop-db

Wait about a minute, then reload the browser.

You get:

    Cannot reach the database
    The web server is running. The database is not answering.

Look carefully at what is still true:
  - EC2 is running. Check it: the page loaded, so httpd answered.
  - PHP is running. It printed that message.
  - The code has not changed at all.
  - Only the database is gone.

THIS IS THE LESSON. When a ticket says "the site is down", this
is very often what is actually happening. The site is up. What it
depends on is not. Your job is to tell which one it is - and now
you have seen the difference yourself.


------------------------------------------------------------
 STEP 10 - Bring it back
------------------------------------------------------------
    aws rds start-db-instance --db-instance-identifier workshop-db
    aws rds wait db-instance-available --db-instance-identifier workshop-db

Reload the browser. Both rows are back. Nothing was lost.
The data lives in the database, not in the page.


------------------------------------------------------------
 STEP 11 - DELETE EVERYTHING  (do not skip this)
------------------------------------------------------------
WHY: a database you forgot about is the most common surprise bill
in AWS. Also, "stopped" is not "free forever" - RDS starts a
stopped instance again by itself after 7 days.

    aws rds delete-db-instance \
      --db-instance-identifier workshop-db \
      --skip-final-snapshot

--skip-final-snapshot matters. Without it AWS keeps a snapshot
behind, and snapshots cost money quietly.

Check it is really gone:

    aws rds describe-db-instances --query 'DBInstances[].DBInstanceIdentifier'

Then terminate the EC2 instance in the console
(EC2 -> Instances -> select -> Instance state -> Terminate).

And remove the security group once nothing uses it:

    aws ec2 delete-security-group --group-id $DBSG


============================================================
 WHEN SOMETHING DOES NOT WORK
============================================================

The browser just spins, no page at all
  -> EC2 security group is not allowing HTTP (port 80) from you.
     Also check:  sudo systemctl status httpd

Page downloads as a file, or you see the PHP code as text
  -> PHP is not installed or httpd was not restarted:
     sudo dnf install -y php php-mysqlnd && sudo systemctl restart httpd

"Cannot reach the database" and you did NOT stop it
  -> Most likely one of these, in this order:
     1. The endpoint is typed wrong. Copy it again from step 4.
     2. The EC2 security group was never added to the DB group (step 5).
     3. The database is still starting. Run:
        aws rds wait db-instance-available --db-instance-identifier workshop-db

"Access denied for user 'admin'"
  -> Password is wrong, or it has a character RDS rejected. Reset it:
     aws rds modify-db-instance --db-instance-identifier workshop-db \
       --master-user-password 'NewPassword123' --apply-immediately

"Unknown database 'workshop'"
  -> You skipped CREATE DATABASE in step 6.

"Table 'workshop.messages' doesn't exist"
  -> CREATE TABLE in step 6 did not run. Run it again.

mysql command not found on your laptop
  -> Skip it. Do step 6 from the EC2 box instead, after step 7:
     sudo dnf install -y mariadb105

It worked yesterday, today it says cannot connect
  -> Your home IP changed. Add the new one - see the note at the
     end of step 2.


============================================================
 WHAT TO SAY IN AN INTERVIEW
============================================================

"How would you check whether an outage is the app or the database?"

  Look at whether the web server is answering at all. If the page
  loads but shows a data error, the app and the web server are
  healthy and the database or its network path is the problem.
  Then check the database status, then the security group, then
  the credentials.

That answer is worth more than the names of ten AWS services,
and you just did it with your own hands.
